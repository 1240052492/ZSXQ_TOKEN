# WP-00 测试计划：源码、许可证与兼容性审计

## 目标与当前边界

WP-00 的目标是冻结 `QuantumNous/new-api` 与 `1240052492/LocalMiniDrama` 的真实输入，证明后续工作包使用的是可复核的 commit、依赖和许可证边界。本仓库当前未包含两个上游业务源码，因此本计划将“尚未取得源码”视为阻断条件，不得把设计文档或空目录标记为 `passed`。

验收关联：`M01`（P0）。

## 输入与固定格式

审计必须建立以下文件（建议存放在 `docs/evidence/WP-00/`，不提交密钥）：

- `source-baseline.md`：仓库 URL、commit SHA、分支、抓取时间、源码目录哈希、构建入口。
- `commit-manifest.json`：两个上游及其子模块/派生仓的机器可读版本清单。
- `dependency-inventory.json`：运行时、直接依赖、锁文件哈希和许可证识别结果。
- `sbom.spdx.json` 或 `sbom.cdx.json`：由可复现工具生成的 SBOM。
- `license-review.md`：AGPL-3.0、LocalMiniDrama 派生关系、第三方依赖及对外服务义务结论。
- `interface-diff.md`：认证、钱包、模型、任务、存储和队列接口差异。
- `migration-risk.md`：数据迁移、账号/钱包替换、供应商密钥隔离和回滚风险。
- `test-report.md`：按本计划记录命令、版本、结果、失败重现和证据链接。

任何证据若包含 token、私钥、供应商密钥、完整用户提示词或支付敏感数据，必须先脱敏；原始敏感材料不得进入 Git。

## 测试矩阵

### 1. 数据层测试

| 编号 | 检查 | 执行方式 | 通过标准 |
|---|---|---|---|
| D01 | 上游版本固定 | 对每个来源执行 `git rev-parse HEAD`、`git status --porcelain`、源码目录哈希；将结果写入 `commit-manifest.json` | commit、分支、抓取时间和哈希齐全；工作树无未记录改动 |
| D02 | 依赖和锁文件完整 | 读取 `go.mod/go.sum`、`package.json/*lock`、`requirements*.txt/poetry.lock`、容器基线等实际存在文件 | 每个运行时依赖有版本、来源和许可证；缺失锁文件必须列为阻断项 |
| D03 | SBOM 可重建 | 使用项目实际生态工具生成 SPDX 或 CycloneDX，并记录工具版本与命令 | 同一 commit 在干净环境生成的组件集合和版本一致；高风险未知许可证有责任人和处置结论 |
| D04 | 迁移对象清单 | 静态扫描迁移、schema、seed 和配置，列出用户、钱包、订单、模型、任务、素材、审计表 | 能明确哪些对象保留、替换、隔离或禁止复用；无“待确认”关键对象 |

### 2. 功能/审计测试

| 编号 | 检查 | 执行方式 | 通过标准 |
|---|---|---|---|
| F01 | 两个项目可从固定 commit 获取 | 在临时目录按 `source-baseline.md` 的 URL/SHA 克隆或下载，禁止使用浮动分支 | 远端可达且 commit 存在；失败时记录为 `blocked`，不得继续声称 WP-00 完成 |
| F02 | 上游最小构建/依赖安装 | 使用各项目官方入口，在干净环境执行安装和最小构建；记录 Node/Go/Python/数据库版本 | 构建成功，或对每个失败给出可复现日志、上游缺陷和解除条件 |
| F03 | 本地账号/钱包/供应商直连盘点 | 使用 `rg` 扫描注册、登录、余额、扣款、支付、API key、provider URL、直连 SDK 等符号，再人工核对调用链 | 每个命中项有文件、用途、替换/隔离决定；未审计命中项阻断 |
| F04 | 许可证边界审查 | 对源码许可证、NOTICE、第三方依赖许可证和网络服务部署方式逐项核对 | `license-review.md` 有负责人、日期、结论和证据；结论为 `pending` 时生产发布门禁保持阻断 |
| F05 | 接口差异与兼容风险 | 盘点认证、模型目录/代理、报价/计费、任务状态、素材和回调接口，形成差异表 | 每个后续工作包能引用明确的输入/输出、错误和幂等语义；未定义的跨服务直连阻断 |

### 3. 模拟操作/数据流测试

WP-00 没有可交付的用户界面，但必须模拟后续关键链路的数据来源，防止审计遗漏：

| 编号 | 场景 | 操作 | 通过标准 |
|---|---|---|---|
| C01 | 统一身份替换 | 从 LocalMiniDrama 入口追踪注册/登录/会话创建调用到 New API 的对应边界 | 能指出本地账号、密码和 cookie 的删除/隔离位置；跨域长期 token 不进入 URL |
| C02 | 统一钱包替换 | 追踪一次任务从报价、预扣、供应商调用到结算/退款的调用链 | 画布仅产生业务事件/结算请求；未发现余额写入或第二套钱包 |
| C03 | 模型与任务兼容 | 将画布节点能力映射到模型目录、协议适配器和参数档位 | 每个节点都有来源、能力标签、协议和失败路径；不兼容节点有明确拒绝策略 |
| C04 | 素材与密钥边界 | 追踪上传、生成、下载和 provider 配置读取路径 | 用户只能获得受控对象访问；管理员配置和供应商密钥不进入浏览器或日志 |

每个场景需附调用链图或文本时序、关键文件/符号、未决风险和证据链接；“代码搜索无结果”不能单独证明不存在运行时路径。

### 4. Smoke 测试

| 编号 | 检查 | 命令/证据 | 通过标准 |
|---|---|---|---|
| S01 | 本仓库验收门禁 | `python scripts/validate_acceptance.py` | 输出 `Acceptance matrix valid`，且 `M01` 未被错误标记为 `passed` |
| S02 | 许可证声明完整性 | 检查上游 `LICENSE`/`NOTICE`/版权归因文件是否随制品保留 | 记录来源和声明文件；本仓库不执行人工许可证审查门禁 |
| S03 | 安全扫描 | `git grep -nI -E '(ghp_|PRIVATE KEY|AKIA|password...)'`，排除模板文件 | 无凭据形态内容；扫描结果保存到 `test-report.md` |
| S04 | 证据完整性 | 校验 `source-baseline.md`、`commit-manifest.json`、`dependency-inventory.json`、`license-review.md`、`test-report.md` 是否存在且字段齐全 | 所有必需字段可复核；缺失文件或敏感信息均阻断合并 |

## 执行顺序与结果状态

1. 先运行 S01-S03，确认本仓库门禁和文档基线正常。
2. 获取并冻结两个上游来源，执行 D01-D04 与 F01-F05。
3. 根据源码真实调用链执行 C01-C04，补全接口差异和风险登记。
4. 再运行 S04，生成 `test-report.md` 并在 PR 关联 `M01`。

结果只能使用：

- `passed`：所有 P0 检查有可复核证据，且合规负责人确认许可证结论；
- `in_progress`：已开始但仍有未完成检查；
- `blocked`：源码不可获得、commit 不可复现、许可证边界未确认或存在未处置的账号/钱包/密钥路径；
- `planned`：尚未执行。

WP-00 在 `license-review.md` 为 `pending`、上游源码未固定或 F01/F02 无法复现时必须保持 `blocked` 或 `in_progress`，不能关闭，也不能放行 WP-01 之后的生产性实现。

## 合并标准

提交 WP-00 的 PR 必须：

- 标题符合 `[WP-00] ...`，描述关联 `M01`；
- 附 `test-report.md` 和全部证据路径，不能只写“审计完成”；
- `docs/acceptance/matrix.json` 中 `M01` 状态与证据一致；未完成不得写 `passed`；
- 通过 `Acceptance Gate`、`Security Gate`；许可证审查不再作为本仓库合并门禁。
- 至少一名 CODEOWNER 审核，且无未关闭 P0/P1 风险；
- 明确后续 WP-01/WP-02 可引用的 commit、依赖、接口和禁止复用清单；
- 提供回滚/撤销审计产物的方法，不提交任何秘密材料。
